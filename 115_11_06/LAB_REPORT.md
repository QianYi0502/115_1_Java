## A–D：觀察、推論與說明

A：平行陣列若漏記某步能源，索引會錯位，甚至在讀取不存在的索引時出錯；一個 MissionStep 同時保存 command、energy、result，避免不同清單錯配。

B：`MissionStep first = new MissionStep(1,14,"成功")` 中 `new` 建立物件，`first` 保存參考值；另一個 `new` 建立的是獨立物件。建構子用 `this.energy = energy` 區分欄位與參數。三個欄位設為 private，getter 只讀，不提供 setter；`main` 是 static 不代表每筆紀錄的欄位要 static。

C：`RoverBattery` 負責能源更新與上下界，`MissionStep` 負責記錄一次已發生的結果，`MissionLog` 負責指令流程、日誌及輸出。資料與行為放在各自負責的類別。

D：同一物件加入清單兩次，清單有兩個參考，但不是兩個快照；若之後改動物件，兩筆看到的都是新狀態。因此應在每次行動後建立新的 MissionStep。Java 傳入的是參考值的副本，不是複製整個物件。

## E：實作檢核

E1：三個 getter 各回傳實例欄位；`isSuccessful()` 使用 `"成功".equals(result)`，即使 `result` 是 `new String("成功")` 也應判為 true。

E2：每筆已讀指令在執行後建立快照；回放依索引讀取；返回單獨計數，不算成功或拒絕；最低能源從首筆起算，空清單顯示「無紀錄」。

E3：上面六組為程式實際輸出，與老師簡報的預期終態及停止筆數相符。

## F1：SampleCase 設計卡（依需求推論，非程式實測）

類別：`SampleCase`，只負責單一樣本盒的容量與存量。private int capacity、private int count；建構子 `SampleCase(int capacity)` 把容量限制到 1～8，count 設 0。公開 `boolean store(int amount)`（非正數或超過剩餘空間整批拒絕、不改狀態）、`int getCount()`、`int getFreeSpace()`、`int unload()`（回傳原存量並清空）。不提供任意修改存量的 setter。恆成立：`1 <= capacity <= 8`、`0 <= count <= capacity`。

容量 3 的呼叫預測：store(2)→true、count=2；store(2)→false、count=2；store(1)→true、count=3；unload()→3、count=0；unload()→0。

## F2：教師模擬錯誤建議審查

1. `public count` 允許 `box.count=-1`，違反外部不得任意改寫存量。
2. `public capacity` 允許 `box.capacity=0`，違反容量須在 1～8。
3. `void store` 讓 `boolean ok=box.store(2)` 無法編譯，違反呼叫端要知道成敗。
4. `count += amount` 使容量 3 連續存 2 後變 4，違反整批拒絕。
5. 沒有 unload，無法執行卸空並取得份數。

驗收 Prompt：請設計 Java SampleCase，private capacity/count，建構容量限制 1～8 並初始為空；store(int) 回傳 boolean，非正數與超量整批拒絕且不改存量；提供 getCount/getFreeSpace/unload，不提供 setter；不用繼承、例外、record、Lambda；列出容量 3 的上述五步預期，不要聲稱已實測。

## F3：錯誤副本反例分析

選擇「用 == 比較成功字串」。預測：`new MissionStep(1,14,new String("成功"))` 的 `isSuccessful()` 可能錯誤回傳 false；原因是 `==` 比較參考而非內容。最小修正：改成 `"成功".equals(result)`。此段是根據 Java 語意的反例推論，未將錯誤版本當作已實測的學生操作。正式版本六條路線的完整執行輸出已列於 E3。

## F4：反思

MissionStep 是歷史，建立後只讀；SampleCase 的存量會變，但必須透過規則化方法。只看最終能源無法證明每筆快照正確。MissionLog 負責在行動後取得能源與結果、選擇建立快照的時機；MissionStep 負責保存收到的值。
