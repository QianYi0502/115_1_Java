## A–C：預測與類別關係

A：MissionStep 保存歷史快照；MissionLog.runMission 在方法內建立 Rover 與 Mission，因此是相依而非欄位關聯；傳遞物件參考不會複製物件。預設腳本結果預測為能源 6、樣本 5、成功行動 3。

B：UML `+` 是 public，`-` 是 private，`~` 是 package；`名稱 : 型態` 為成員表示法。實例 getter 不應畫 static 底線。MissionStep 的三個私有欄位及 getter 是只讀快照的證據。

C：Rover 負責能源、樣本、成功行動與 execute 停止保護；Mission 負責腳本迴圈、返回、歷史與摘要；MissionLog 負責組裝任務及輸出。Mission 以欄位連一個 Rover，並以 ArrayList 連 0..* 筆 MissionStep；MissionLog 在方法中使用三者，為相依。

## D：程式修改與重構驗證

D1：`run` 在已返回或 Rover 停止時不再讀指令；每次 execute 後才建立 MissionStep；遇指令 0 設 returned 並停止。

D2：`countOk` 用 isSuccessful 累計；`lowestEnergy` 空清單回傳 -1，否則從第一筆能源取最小值；不提供 getHistory 以免外部清除或新增紀錄。

D3：六組完整輸出見上方。`{1,1,1,1}` 第三筆達標後第四筆應略過；若錯誤地仍記錄第四筆，會產生多餘「任務已停止」紀錄，即使最終能源仍是 2。這是停止時機的反例推論，並非聲稱已執行錯誤副本。

## E1：樣本盒人工初版設計

SampleCase 保存 private int capacity/count；建構子修正容量到 1～8、count=0；`boolean store(int)` 僅正數且放得下才增加存量；`int getCapacity()`、`int getCount()`、`int getFreeSpace()` 查詢；`int unload()` 卸空並回傳卸下份數。不提供 setter。容量 3 存 2 再存 2：第二次 false，count=2。

## E2：教師模擬 AI 圖審查

1. store 回傳 void：`boolean ok=box.store(2)` 不能編譯，違反回報成功與否。
2. public count：`box.count=-1` 可破壞存量下界。
3. public capacity：`box.capacity=0` 可破壞容量範圍。
4. 直接累加：容量 3，連續 store(2) 會超過容量。
5. 若缺 unload/getFreeSpace，則無法卸空或查剩餘空間。

採納：保留清楚的 capacity/count 概念；拒絕 public 欄位、void store、直接累加與缺少查詢／卸空契約。

## E3：超量反例預測與限制

正確邏輯：容量 3，第一次 store(2)→true/count=2；再 store(2)→false/count=2；store(1)→true/count=3；unload()→3；再 unload()→0。若刪除超量條件，第二次會錯誤變 true/count=4，第三次變 count=5，unload() 回傳 5。以上是依教師簡報提供的案例與程式規則推論；目前壓縮檔沒有 `examples/SampleCase.java` 與 `SampleCaseDemo.java`，因此不能冒稱已執行這兩個程式。D3 的主任務六路線則已獨立編譯執行。

## F：反思

MissionLog 沒有 Rover 欄位，但在 runMission 使用 Rover 區域變數，故仍相依。MissionStep 允許 0..*，因為空腳本可以沒有紀錄，不限預設三筆。Rover 保護停止後狀態，Mission 保護停止後不再讀取或記錄。若交出內部可變清單，外部可能清空日誌。複製 Rover 做 HeavyRover 會重複狀態與停止規則，後續修改容易不一致。
